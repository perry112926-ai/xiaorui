# 生活服务与执行边界

当前三平台共用 Agent、候选卡片、确认层和操作台账。瑞幸／滴滴首版以北京为主；麦当劳查询与新增地址接受本轮明确城市，实际配送范围以官方结果为准。已有北京自取和广州外送只读证据。没有自动定位结果时，先询问当前地标；公开测试地点不保存为家庭地址。

## 对用户的能力表达

当前餐饮点餐／外卖只提供麦当劳，不是通用餐饮平台。用户说“帮我点外卖”“订个午饭”时，用一句自然短话交代范围，再推进当前一步，例如：“可以，我现在能帮您点麦当劳。您想吃什么？”用户已选麦当劳后无需反复声明，不在开场堆砌接口、配置和验收术语。

指定其他餐厅或美团、饿了么等未接入平台时，简短说明暂不能代点，可以提出麦当劳作为替代；用户同意前不换商家、不开始替代点单。地图工具可以查询其他餐厅的公开位置，但查到门店不等于接入了该餐厅的菜单、配送或下单。瑞幸是单独的咖啡饮品服务，不代表支持其他餐厅或通用外卖；滴滴属于出行服务。

这条原则适用于整个产品：**只承诺当前工具能执行的动作，只报告已经核实的结果。** 长期愿景、接口存在、凭据已填、测试通过分别不等于功能已交付或业务已完成。允许说“帮您查菜单、核对费用”，不能在官方结果前说“已经点好、付好、马上送到”。没有真实提醒、通知、主动分享或联系他人的执行能力时不能承诺后台替用户完成；当前不支持的支付、修改订单、催单、退款等，到了相关步骤简短解释，并给出官方处理入口或下一步。技术限制与验收缺口在本文和验收清单完整保留，不向老人一次讲完。

运行模式也属于能力边界：设置 `XIAORUI_READ_ONLY=1` 的预览只允许查询，应说“可以帮您查麦当劳菜单和价格”，不能说能提交订单、新增地址或叫车。普通模式也仍受凭据、交易开关和具体方案确认约束；代码里有执行分支不等于当前会话可执行。

## 各平台能力

| 服务 | 已实现路径 | 关键限制 |
| --- | --- | --- |
| 麦当劳 | 真实门店、菜单／套餐选项、同店多餐品购物车、数量与预算、官方取餐方式、已有／新增配送地址与门店、含费核价、方案、本人订单和取消条件查询 | 新增地址需核对城市、地址、门牌、联系人及完整手机号并独立确认；套餐轮次目前单选；不保证过敏安全或特殊改配；已支付修改／退款走官方渠道 |
| 瑞幸 | 坐标查店、饮品详情、真实温度糖度等 SKU 切换、数量与预算、预览核价、方案及本人订单状态 | 外送未验收；取消费用规则不明时不自动取消；历史未知创建请求仍需核查，不能重试诊断 |
| 滴滴 | 地点与实际接送点、车型估价、待确认叫车、本人订单／司机位置与取消条件查询 | 预估不是最终车费；确认可能免密扣款；预约、修改进行中目的地、投诉退款未实现 |

三平台实际写操作只由宿主执行，不暴露为模型工具。代码中存在创建／取消分支，不等于真实交易验收通过。本人订单通过 owner 所属操作记录查询，禁止使用猜测的订单号或他人候选。

## 必须保留的业务规则

- 重新查询失败时清空旧候选；门店、商品与车型必须来自本轮有效结果，不能靠序号或名称猜测。
- 闭店信息明确时拒绝准备即时订单；没有营业字段时不根据时间推断开闭店。
- 明确预算保存在本地请求中，准备与确认重核价均校验；超预算直接停止，只有用户调整预算后才能重新准备。
- 核价覆盖商品、数量、SKU、履约方式、地址、实际接送点和返回费用。改变实质内容需重新确认，缺少费用分项不能当零。
- 外送要核对完整地址、餐具和总额；麦当劳备注不代表商家保证接受。确认前再次查询配送资格，范围失效或闭店则停止。
- 取消必须先核实订单状态、可取消条件及明确费用；请求被接受不代表最终已取消或已退款。
- 写入超时或陌生响应先私有持久化并标记未知，不通过再次创建查原因；重启不重放写操作。

## 当前真实证据与缺口

2026-11-05 新一轮[真实接口验收](acceptance/services-live-2026-11-05.json)：三平台生产场景适配器均完成查询、待确认卡片与重新核价；仅用北京公开测试地点，没有创建订单、付款或叫车。滴滴曾在二次核价返回官方限流码 `-32001`；减少选车型时的重复估价后复测通过，正式确认仍重新核价。

麦当劳另通过真实模型调用正式 HTTP 路由的三轮聊天：选店、选麦香鱼单品、生成外带方案，确认卡片可重新读取；测试使用进程内 ASGI 请求，未验证浏览器操作。广州已有地址的外送含费核价及重新核价通过，未创建配送订单。独立受控实验创建过一笔真实待支付订单并取得官方支付入口，未付款；网页完整交易仍待验收。

瑞幸真实查店、饮品、规格切换和预览通过。此前一次创建请求结果未知，用户小程序未看到订单也不足以排除延迟或账号差异；没有可核实订单号时保留保护，不自动重试。

滴滴真实地点、估价、待确认方案与跳转链接通过，没有真实发单、接单或扣款验收。平台吸附出的实际上下车点可能不同于原地点，必须重新核对。

所有测试价格都是当次快照，不作为当前报价。真人语音、真实消费、支付入口和进度要按[验收清单](acceptance.md)逐项验证。

## 开发接口与复现

场景模块提供 `schemas`、`dispatch`、`quote`、`execute`、`query_order`；`ActionManager` 负责确认与一次性执行。工具发现和参数以账号实际返回 schema 为准，MCP/HTTP 成功后仍检查业务结果。

只读检查：

```sh
uv run python experiments/life_services_probe.py luckin
uv run python experiments/life_services_probe.py didi
uv run python -m experiments.services_acceptance --live mcd luckin didi
uv run python -m experiments.mcd_chat_acceptance --live
uv run python -m experiments.mcd_delivery_acceptance --help
```

广州外送实验需由用户选定实际返回地址和候选；历史序号不可复用。账号、地址、支付链接及原始响应只保存在忽略的本地目录。

本机代理无法访问国内官方服务时，可在 `.env` 配置 `LIFE_SERVICES_TRUST_ENV=false` 直连；默认 `true` 沿用环境代理。只影响生活服务 MCP，不改变模型连接，也不会自动重试交易。新验收脚本阻止交易写入，报告存入 `.local-data/`，不能以运行脚本代替真实消费确认。

官方参考：[麦当劳工具目录](https://github.com/M-China/mcd-mcp-server)、[瑞幸 MCP](https://open.lkcoffee.com/mcp)、[滴滴 MCP](https://mcp.didichuxing.com/)。

## 滴滴取消入口（2026-11-05）

真实叫车记录现在提供“查看取消条件”，使用本人记录 ID 调用 `/api/actions/{id}/prepare-cancel`，不依赖模型猜测订单。接口只查询并准备方案，不直接调用取消；费用已明确后仍需“确认取消”。其他用户记录不可访问，明确不可取消时即使取消费为零也拒绝准备。失败提示会显示并播报。

官方当前工具目录提供 `taxi_cancel_order(order_id, reason?)`，没有独立取消费预查询工具；本次订单查询遇到限流，不能凭旧状态或缺失费用断定免费取消。费用未知时继续要求到滴滴 App／小程序进行中订单办理。卡片的“取消这个方案”仅放弃未提交方案，与取消真实行程不同。查条件不代表取消成功，真实取消执行和取消费仍需单独验收。本次修复没有实际取消、重复叫车或扣款。

## 在新地方点麦当劳外卖

`mcd_current_location` 读取本轮、当前用户的有效浏览器定位，通过官方地图逆地理编码返回附近地址；失败时询问收餐地址，不猜门牌。城市必须由用户明确或通过本轮定位核对，不能从其他城市的旧地址猜测。`mcd_prepare_address` 收齐用户核对的城市、地址、门牌、联系人和完整手机号后生成“新增配送地址”卡片。性别仅在用户提供时填写，掩码手机号不可提交。

用户点击或准确说“确认新增地址”后，宿主调用官方 `delivery-create-address`，信息保存至麦当劳账号，不覆盖小瑞家庭资料。地址创建独立于订单开关；成功后重新查询配送地址，选择新地址继续查询可送门店和餐品。下单仍需另外核价和确认。写入结果未知时持久化保护，不自动重复创建。

新增地址确认、账号隔离、重复提交和未知结果保护、创建后查店由自动化流程覆盖；官方逆地理编码契约及麦当劳工具目录可在线核查。尚未使用真人完整联系方式创建新地址，真实写入和实际配送仍待逐项验收。

老人点餐完整路径、修改与异常场景、真实证据和人工处理边界见[老人点餐场景清单](acceptance/mcd-elderly-scenarios.md)。同店可分次添加／修改／删除购物车餐品，再核价整单；换店或换地址清空。新地址可分步收集，缺项一次只问一个；中文数字手机号仅作确定的数字规范化，仍需完整复述核对。

## 能力表达一致性检查（2026-11-05）

本轮检查 README、产品理念、交互设计、系统提示、自动加载的场景 Skill、工具返回说明和订单卡片。

| 发现的问题 | 已统一的表达 |
| --- | --- |
| 泛化“点外卖”没有明确商家范围 | 一句说明当前麦当劳范围；未接入餐厅不可代点，不擅自换商家 |
| 系统提示和麦当劳 Skill 仍写仅北京地址、不能新增地址 | 按当前城市、新地址草稿、独立确认及购物车流程说明；实时可配送仍须查官方 |
| 旧自取 Skill 与新场景流程并存 | 标明旧流程仅用于兼容，新的点餐和外送优先 mcd 工具 |
| 旧瑞幸预览文案容易被理解为整个项目不能创建饮品订单 | 明确仅该工具是预览，后续走饮品场景的受控确认；卡片称“饮品方案” |
| 尚无提醒执行能力却先说“帮您记着”，再补充不能保证通知 | 直接说明目前不能到时主动提醒，给出手机闹钟等下一步，不声称已安排 |
| 通常点餐流程可能被误用于只读预览 | 当前运行模式优先；只读时只说能查菜单、价格，不说能下单，不向老人使用“只读模式”等术语 |
| 产品愿景可能被当作当前能力 | 产品理念明确区分理想态；提醒、主动通知、视频分享等未交付能力不能对外许诺 |

真实模型回归覆盖泛化外卖、午饭、明确拒绝换商家的肯德基、饿了么家常菜及定时提醒，并分别检查普通／只读模式。完整响应仅留在忽略的本地报告；公开结果见[能力边界验收](acceptance/capability-boundary-2026-11-05.json)。这验证代表性案例，不保证模型所有未来措辞；真实消费与各平台履约能力仍按前述验收边界执行。

复现：`.venv/bin/python -m experiments.capability_boundary_acceptance --live`；只读模式另加 `--read-only`。实验使用隔离会话和只读商户适配器，不创建地址、订单、付款、提醒或对外消息。

## 麦当劳默认点餐闭环

泛化点餐请求简短说明“现在可以帮您点麦当劳”。已有收餐地址或自取地标后，默认一人、需要餐具，结合已知用餐偏好和本次要求自动选可用门店；最多推荐三份有官方图片、可构建搭配并已通过含费核价的单人套餐。不强制先问预算；用户给了预算则准备与确认均遵守。明确只要单品时也可预核价带图推荐。

选择推荐直接准备最终确认，保留加餐时已有搭配、餐具和备注；最终卡片包含图片、默认内容、实际收餐地址、可取得的电话尾号及总额。地址在准备和确认时按官方记录核对。新增地址仍按独立授权保存；不能用定位猜联系人或房号。推荐过期、闭店、价格或库存变化时重查并显示新候选／新总额；预核价不能保证之后永远有库存。

明确确认具体方案后创建待支付订单，前端取得有效官方 HTTPS 入口后结束通话并在新标签页打开付款。系统不替用户付款。合成语音通话和文字已通过真实模型、官方菜单及核价到最终确认卡片；实际 Chrome 麦克风接通且收到识别，文字外送已到真实官方扫码支付入口；完整实际麦克风点餐尚未完成验收，助手不执行扫码付款，详见[记录](acceptance/mcd-call-checkout-2026-11-05.json)。

支付入口在新标签页打开，小瑞原页面保留。若浏览器拦截自动弹窗，可点击已创建订单卡片上的“打开官方支付入口”链接；不为打开页面重复创建订单。
